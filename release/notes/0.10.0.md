# Runx CLI 0.10.0

Runx 0.10.0 rebuilds the core around connectors. Every external read and write
is a declared connector operation, run under an instance the operator bound,
admitted against its grant and approval, confirmed by its own readback where
the provider can be read, and sealed in a receipt that states only what was
declared or observed. Skills are graphs of five step kinds in `run.yaml`, and a
runner with no steps is one agent turn the attached agent works by calling back
into the run. This release breaks the 0.9 skill, credential and receipt
contracts; read the breaking changes before upgrading.

## Highlights

- Connectors: a `runx.connector.v1` manifest declares each operation's request,
  credentials, approval, effect and readback. The kernel admits the call,
  performs it once, reads it back and seals it; no skill holds a credential.
- One skill format: `run.yaml` runners are graphs of `agent`, `operation`,
  `tool`, `ask` and `skill` steps, with one reference syntax for inputs, step
  results and acts.
- Agent turns: a runner with no steps is one turn. The agent's calls into the
  run (operations, tools, asks, skills) are each admitted and recorded, and an
  open turn can be served as MCP tools.
- Receipts state only what their issuer declared or observed, carry typed
  observations, and are signed by the runx home's own local identity unless a
  hosted or CI signer is configured.
- The managed agent speaks the Anthropic Messages and Chat Completions
  dialects, with built-in Anthropic, OpenAI and Gemini profiles.

## Added

- `runx connector list|inspect|instances|use|revoke|import-mcp` to read
  connector manifests, bind and select instances, and pin the tools an MCP
  server serves.
- Connector implementations over declared HTTP requests (with readbacks,
  paging, rate-limit halts and repeated writes), MCP over HTTP or stdio,
  process tools and data stores (`store`: SQLite, PostgreSQL, Redis).
- Plugin repositories: a directory holding `connectors/` and `skills/` serves
  its own connectors to the skills inside it.
- `runx skill --act <json>` states the act a run is invoked with; operation
  steps carry `act:` and connectors declare the `effect` a write makes.
- `runx turn <run-id>` serves the agent turn a paused run waits on as MCP
  tools over stdio.
- `runx config unset`, and the managed agent's `dialect` and `endpoint-url`
  under `runx config set`.
- Harness cases bind connector credentials and sessions in `setup`, answer a
  request declared more than once in declared order, and fail when a declared
  exchange is never requested.
- Governed skills for Nitrosend test sends, Reddit account workflows, Google
  Calendar reads, GitHub `issues.create` and list hygiene review.
- Registry package metadata names the connectors a package declares and the
  operations it lists for each.
- `runx skill inspect` records a registry ref its `RUNX_REGISTRY_DIR` does not
  hold as an unresolved edge, so a host can supply those skills and inspect
  again.

## Changed

- One protected kernel store per project holds runs, instances, custody and
  usage; every runx location resolves from `RUNX_HOME` and
  `RUNX_PROJECT_DIR`.
- Approvals are addressed by the step that asks (`<child>#<step>` below the
  root), and resume answers are read from one document on stdin.
- Graph references read values, not artifact envelopes.
- A skill package is validated, and a packet schema parsed, once per exact
  source in a process, so a run no longer re-parses them at every step.
- x402 advertises the `runx.invocation` schema by reference, and paid
  invocations carry attribution.
- Contracts emit closed string enums as `enum`, and the x402 upstream is pinned
  to `@x402/core` 2.27.0.
- `runx skill -i name=value` reads each value by the type its runner declares
  for that input, and refuses an input the runner does not declare;
  `--input-json` still takes JSON.

## Fixed

- A declared request whose optional query values are all absent no longer
  ends its URL in a bare `?`.
- Pinned registry version reads are isolated from other versions.
- The vendor presentation is kept out of the payment quote fingerprint.
- Suspended run outcomes survive a resume, and plugin connectors bind from the
  directory runx was invoked in.
- A missing connector error names where it was looked for.

## Removed

- `X.yaml` execution profiles, and the runner source kinds `cli-tool`,
  `javascript`, `mcp`, `external-adapter`, `thread-outbox` and `approval`.
- The graph-language `fanout:` groups, step `retry:`, `charter_from` and
  `mint`. Fan-out and retry now belong to the driving agent and the host: the
  agent fans out inside its turn by calling the child skills in its allowance,
  bounded by `max_fanout` and `max_child_depth`, and the kernel retries effects
  within their declared tolerance.
- `runx credential bind`, `runx connect bind`, `runx data migrate`, the
  `--profile` and `--auth-mode` flags of `runx credential set`, `runx skill -p`,
  `runx login --from-gh`, and `runx publish --token`.
- The built-in GitHub CLI driver, vendor reference kinds and vendor rules in
  the core; vendor behavior lives in connector manifests.

## Security

- Credentials are delivered only to the operation that admits them, scrubbed
  from refusal and provider answers, and tracked per field for multi-field
  secrets. A process tool receives its credential only in the variable its
  manifest names.
- Local receipts are signed by a key unique to each runx home instead of a
  shared fixture key, and the hosted demo key is named by the id it derives.
- Harness cases run in their own home and project with ambient grants and
  connector credentials removed, and never reach the network.
- A workspace `.env` may not set Runx's own `RUNX_` variables, so a cloned
  repository cannot redirect Runx's state, Connect or signing, or supply host
  authority.

## Breaking changes

- Skills: rename `X.yaml` to `run.yaml` and express each runner as a graph of
  the five step kinds. External calls become `operation` steps against a
  connector; removed runner kinds have no compatibility path.
- Credentials: bind each connector once with
  `runx credential set <connector> --credential <name> --from-stdin`, or
  select an instance with `runx connector use`. Profiles bound by
  `runx credential bind` are not read.
- Receipts: the 0.9 shapes are not produced. Act and decision fields appear
  only when stated, and local receipts verify against the home's own key.
- Approvals and answers keyed by request ids from 0.9 runs do not resume on
  0.10.
- `RUNX_AGENT_PROVIDER` selects a built-in profile or a provider configured by
  dialect and endpoint; `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` or
  `GEMINI_API_KEY` supplies the key.

## Upgrade guidance

- Install with `npm install --global @runxhq/cli@0.10.0`, Homebrew, Scoop, or
  the matching release archive, then confirm `runx --version` reports
  `runx-cli 0.10.0`.
- Rebind credentials with `runx credential set`, then check each connector
  with `runx connector inspect <connector>`.
- Convert skills to `run.yaml` and run `runx harness <skill-dir>` before
  publishing; `runx skill inspect` shows how a runner resolves.
- Finish or discard runs paused under 0.9 before upgrading.
- Local signing refuses a keys directory other users can write. If `runx`
  names `~/.runx/keys` as writable, restrict it with `chmod 700 ~/.runx/keys`.
